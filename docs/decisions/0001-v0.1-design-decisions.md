# 0001: v0.1 design decisions

**Status:** accepted (2026-09-16)
**Context:** `llikert_development_plan.md` settles scope and scoring semantics. `docs/implementation-plan.md` details the open implementation choices. This record lists the choices the owner has accepted, so later records can refer to them by number.

## Confirmed by the owner

- **C1:** The R API uses the development plan's names: `scoring_task()`, `scorer_connect()`, `prepare_task(task, engine)` and `score_texts(texts, ids, task, engine, ...)`.
- **C2:** The R result is an S3 `llikert_result` that subclasses a tibble. It is wide and keeps input order: `id`, then `expected_value` (numeric tasks only), then one conditional-probability column per category id. Everything else is stored as attributes and read through accessors.
- **C3:** The first model profile is Qwen3-4B-Instruct-2507, and Qwen2.5-0.5B-Instruct (Q8_0) is the small smoke and CI model. *Weight format superseded by 0002 D23: F32 GGUF on CUDA, not Q8_0.*
- **C4:** Checkpointing is off by default. When N > 200, the client prints a one-time hint.
- **D19:** The result accessors carry the prefix `llikert_result_`: `_diagnostics`, `_candidate_probs`, `_candidate_log_probs`, `_categories` and `_manifest`.
- **D21:** Both packages are released under the MIT license.
- **D22:** Build against a current llama.cpp release from the start. The llama-cpp-python binding is built from source with its vendored llama.cpp moved to a pinned release tag. Any mismatch in function signatures or struct layouts is fixed with a narrow shim in the private adapter, and a test checks the shim.

## Accepted recommendations

D1–D18 and D20 are accepted as written in `docs/implementation-plan.md`. They cover template allowlist rendering, segment tokenization, the answer-boundary check with code suggestions, the prepared artifact sent back with every score request, JCS hashing, the fingerprint composition, the auth modes, preview on `/v1/prepare`, single-worker concurrency, client input semantics, the retry and chunk policy, the shared result format, and the Python client stack.

## Consequences

Any change to these decisions needs a new record that supersedes the item it changes.
